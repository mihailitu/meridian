# Architecture Audit — 2026-05-02

Findings from comparing `next-gen-trading-platform-design.md` and the iteration plans against the actual codebase. Issues are grouped by priority. Each item lists evidence (file:line), what's broken or missing, and the fix direction.

[`strategy-logic-fixes.md`](strategy-logic-fixes.md) already covers the strategy-logic fixes (P1 below); this doc is everything else.

## P0 — Bugs that invalidate current results

### A1. Sharpe ratio always reports 0.00
- **Status (2026-05-11)**: portfolio-level Sharpe partially fixed (PR `validation-and-improvements` Phase 2.5). Two changes landed: (1) `PaperBroker.set_current_time` lets the strategy runner advance a simulated clock per bar, so fills are now timestamped on bar time instead of wall clock — `_process_fills` produces a daily curve spread across the simulated period; (2) Sharpe is computed on this cost-basis daily curve. Portfolio Sharpe came out at 0.91. Per-strategy Sharpe is suppressed to N/A when noisy (|x|>10 or <20 trading days in curve) — symptom of the deeper trading-cliff issue below.
- **Still open**: cost-basis equity curve doesn't reflect open positions' market value; mark-to-market would need a working broker cash check first (see new issue C5 below). Without that, MTM equity balloons to fantasy values because PaperBroker accepts unbounded buys.
- **Evidence**: `src/axtrade/fulltest/analytics.py` `_process_fills`; `src/axtrade/oms/broker.py:_current_time`; `src/axtrade/strategies/runner.py` calling `set_current_time(data.bar.timestamp)` per bar.
- **Why it matters**: Equity is flat between fills, daily resampling produces ~0 returns, the Sharpe denominator overwhelms the numerator. Every fulltest report has Sharpe = 0.00, so we have no valid risk-adjusted return metric. Anyone reading current reports cannot compare strategies on Sharpe — a core analytics promise.
- **Fix**: Compute mark-to-market equity using bar prices for open positions during analytics. Requires plumbing bar price data into the analytics step (currently fills-only). Until fixed, suppress Sharpe in reports rather than printing a misleading 0.00.

### A2. Indicator engine → strategy wiring is incomplete
- **Evidence**: `src/axtrade/strategies/base.py:25-35` — `BarWithIndicators` carries only `sma_20`, `rsi_14`, regime, trend, trend_strength, volatility. No `bb_upper`, `bb_lower`, `bb_middle`, `atr`. `src/axtrade/strategies/mean_reversion.py:6,40-57` recomputes Bollinger Bands locally from a private price buffer, duplicating work the IndicatorEngine already does upstream.
- **Why it matters**: The IndicatorEngine was built to be the single source of truth for indicators, but strategies bypass it for anything beyond SMA/RSI. The redundant computation diverges from the canonical values used in regime detection and discovery scoring, and the design pillar of "indicators flow once through the pipeline" is broken in practice.
- **Fix**: Add `bb_upper`, `bb_lower`, `bb_middle`, `atr` to `BarWithIndicators`. Have the aggregator populate them from `IndicatorEngine`. Strip the local Bollinger buffer from `MeanReversionStrategy` and any other strategy that recomputes.

### A3. IBKR adapter silently drops dynamic-subscribe requests
- **Evidence**: `src/axtrade/gateway/base.py:44` defines `add_symbols` as a no-op default. `src/axtrade/gateway/ibkr.py` only overrides `subscribe`, not `add_symbols`. `MockAdapter` and `AlpacaAdapter` do override it.
- **Why it matters**: `DiscoveryRunner._feed_gateway` (`discovery/runner.py:115-148`) publishes `subscribe` events on the gateway control channel; the gateway calls `adapter.add_symbols()`. Under IBKR — the production broker — this becomes a no-op with no error log. The discovery→trading bridge does not actually route discovered symbols to IBKR market data.
- **Fix**: Implement `add_symbols` on `IBKRAdapter` (request market data for the new contracts via `ib_insync`) and `remove_symbols` (cancel market data). Add a test that verifies the bridge end-to-end against a fake IBKR client. Until then, log a `WARNING` from the base class no-op so silent drops aren't invisible.

### A4. 93% order rejection rate distorts every fulltest result
- **Evidence**: `strategy-logic-fixes.md` item 6 — `oms.max_positions: 20` in `config/default.yaml:67` is shared across all strategies. With 5 strategies × 50+ discovered symbols, the cap is hit in minutes; 25,157 orders → 1,832 fills (7.3%).
- **Why it matters**: The strategies are not being tested against a market — they're being tested against a global cap. Even if the entry logic were perfect, we couldn't observe it.
- **Fix**: `strategy-logic-fixes.md` item 6 + 7 (raise fulltest cap to 50, add per-strategy `max_positions`). Treat as P0 because no other fulltest-derived conclusion is reliable until this lands.

## P2 — Drift from the design doc

### B1. Macro regime detection is a per-symbol SMA crossover
- **Evidence**: `src/axtrade/indicators/regime.py` classifies one symbol's 10/20 SMA spread. `RegimeResult` schema has no VIX, breadth, put/call, or correlation fields. The design doc (next-gen-trading-platform-design.md) calls for VIX, advance/decline ratios, put/call, SPY/QQQ/IWM slope, and breadth as a first-class macro signal.
- **Decision needed**: Either rename what we have to "trend regime" (per-symbol, scoped accurately) and accept that macro regime is unbuilt, or commit to building it. Building it requires a new data source (VIX index, A/D line) — non-trivial.
- **Fix direction**: Rename + scope-correct first (cheap, high-clarity). Defer the real macro layer until the strategies have positive expectancy and we know we'd actually use it.

### B2. ML layer is not what was designed
- **Evidence**: `src/axtrade/ml/models.py:118-179` is hand-rolled gradient descent in pure Python (`learning_rate=0.01`, manual weight updates per row). The design doc commits to PyTorch neural-net predictions with GPU training. `ml_prediction` is registered in `STRATEGY_TYPES` but disabled in `default.yaml` and never appears in fulltest results.
- **Decision needed**: Is ML still in scope? If yes, the current `ml/` module needs to be replaced (PyTorch, real feature engineering, train/eval loop, model versioning). If no, delete or clearly mark as scaffolding so it isn't mistaken for a working component.
- **Fix direction**: Delete `ml/` for now; revisit after P0+P1 land. Hand-rolled GD on small feature sets won't beat the rule-based strategies once those are working.

### B3. `BaseStrategy` interface is a subset of what the design specified
- **Evidence**: `src/axtrade/strategies/base.py:78-127` — only `on_bar` is `@abstractmethod`. The design doc lists `on_bar`, `on_tick`, `on_fill`, `on_regime_change` as the four required hooks. `on_fill` exists but is optional; `on_tick` and `on_regime_change` don't exist at all.
- **Why it matters**: Tick-level strategies (e.g., microstructure, latency-sensitive) are impossible. Regime-change events fire from no-one to no-one — strategies have to poll `data.regime` on each bar, which is what the design wanted to avoid.
- **Fix direction**: Add `on_tick(tick)` (optional, default no-op) and `on_regime_change(symbol, old, new)` (optional, default no-op). Wire `on_regime_change` from the IndicatorEngine when `RegimeResult` transitions. Tick-routing requires StrategyRunner to also subscribe to `stream:ticks:*`.

### B4. Global market scope never shipped
- **Evidence**: Hardcoded `stream:ticks:us` in `aggregator/service.py`. `SymbolConfig` defaults to `exchange="SMART"`, `currency="USD"`. No timezone-aware market hours. No multi-exchange routing. The design doc had US in iterations 1-2, EU in 3, Asia in 4.
- **Decision needed**: Headline capability. Honest answer is "deferred indefinitely" — accept that and update the design doc, or commit to building it.
- **Fix direction**: Document as deferred in the design doc. Revisit only if the US strategies are demonstrably profitable. Multi-market is a 4-6 week effort that adds zero value if the strategies don't work.

### B5. Horizontal scaling / worker partitioning is documentation-only
- **Evidence**: Design doc shows worker-1.yaml, worker-2.yaml configs with strategy assignment. No code path supports this. `StrategyRunner` runs all enabled strategies in one process; there is no partitioning, no leader election, no shared-state sync.
- **Fix direction**: Defer. We're nowhere near the throughput where this matters.

## P3 — Operational gaps

### C1. Alert channels = LogChannel only
- **Evidence**: `src/axtrade/alerts/channels.py` has `LogChannel` and `CallbackChannel`. PROGRESS.md iteration 9 marks email/SMS/Slack as "ready" but the channels don't exist.
- **Fix**: Build `EmailChannel` (SMTP), `SlackChannel` (webhook). PROGRESS.md already lists this as iteration 12. Keep it deferred until a strategy is profitable enough to be worth alerting on.

### C2. IBKR live path has never been exercised
- **Evidence**: No integration test for `IBKRBroker.submit_order`. No recorded live-trading session in git history. `oms.paper_mode: true` everywhere.
- **Why it matters**: The first live order submission will be the first real test of code on a live-money path. That's a foreseeable incident.
- **Fix**: Before any live trading, write a paper-account integration test against IBKR's paper TWS — submit a $1 order, verify fill, cancel an open order, reconcile positions. Run from a script, not from production config.

### C2b. Aggregator persistence is single-row INSERT (added 2026-05-03)
- **Status (2026-05-10)**: tried + reverted. The batching premise was wrong. Implemented buffer (size=200, max_age=2.0s) + `bulk_insert_bars` flush; fulltest re-run delivered only **1.6% wall-clock speedup** (2214s → 2178s), not the 10–20× the audit estimated. Worse, the buffer caused discovery to read stale data from the DB — different fed-symbol sets between runs (only 7/20 first-fed symbols overlapped). Ratio of strategy P&L was within 1–3% so strategies themselves weren't broken, but the divergence in discovery output made the change net-negative. The premise that "INSERT was the bottleneck" was disproven — `asyncpg` already pipelines INSERTs concurrently with other work.
- **Evidence**: `src/axtrade/aggregator/service.py:187` — every completed bar is persisted with `bar_repo.insert_bar()` (one INSERT per bar). Pre-seed already uses `bulk_insert_bars` (commit `85566bb`); the live aggregator path is intentionally unchanged. Reports comparing the runs: `fulltest_20260510_105510.txt` (un-modified) vs `fulltest_20260510_113340.txt` (with buffer).
- **Real bottleneck (partial answer, 2026-05-10)**: `strategies/runner.py:285` was dispatching every `strategy.on_bar()` to a thread pool via `loop.run_in_executor`. Removing that dispatch saved **6% wall clock** (2214s → 2080s) with strategy P&L unchanged within natural noise (~$3 drift). Real but modest. The remaining ~94% of wall clock is somewhere else — replay tick generation, Redis stream ops, or OMS rejection path are the next suspects, but not investigated further yet.
- **System non-determinism**: two un-modified runs of the same params produce slightly different results — 22-order drift, 9/20 overlap in first-20 fed symbols, but identical strategy P&L within $3. Strategy-level metrics ARE reproducible; micro-counts and discovery output have inherent run-to-run variance.
- **Why it matters**: Fulltest measured ~50 bars/sec sustained INSERT throughput. A 6-month / 5-symbol replay with S&P discovery generates 200K+ persisted bars; runs that took ~42 min in the past now take 60–90+ min after BB/ATR widened the row payload (commit `b5fe036`). This makes iterating on strategy logic via fulltest impractically slow.
- **Fix direction**: Buffer 100–1000 rows in the aggregator and call `bulk_insert_bars`, or switch to PostgreSQL `COPY` for bar persistence. Expected speedup 10–20×.

### C3. PaperBroker fill assumptions are optimistic for discovered symbols
- **Evidence**: `oms/broker.py` PaperBroker fills at next-bar open + fixed slippage_bps. No volume check, no partial fill modeling. For SPY-class names this is fine; for thinly-traded discovered symbols at full position size, it overstates fill quality.
- **Fix direction**: Add a per-symbol max-volume-pct check in PaperBroker (reject fills that would consume >X% of bar volume). Lower priority than P0/P1 but worth flagging when the maintainer next looks at fulltest realism.

### C4. `axtrade` package vs `meridian` repo name
- **Evidence**: Repo dir `meridian/`, Python package `axtrade`, Postgres user/db `axtrade`, `pyproject.toml: name = "axtrade"`.
- **Fix**: Pick one. If `axtrade` is the actual product name, rename the repo. If `meridian` is the new name, do the package rename in a single PR (touch ~all import sites). Now is cheap; later it gets more expensive.

### C5. PaperBroker accepts buys without a cash check (added 2026-05-11)
- **Evidence**: `src/axtrade/oms/broker.py:submit_order` fills any market buy at the current price + slippage with no check against available cash. In the canonical 6-month fulltest, total buys reached **48,216 shares** for **5,002 sells**, leaving an open-position cost basis of **$4.2M against $100K starting capital**. Realized P&L (from closed trades only) reads $57; mark-to-market equity on the phantom positions reads $824K. The risk manager catches *some* of this via `Position value $X exceeds limit $50000.00` rejections, but the limit is per-position not portfolio-wide, so dozens of open positions stack up unchecked.
- **Why it matters**:
  - It causes the **12-day trading cliff**: strategies max out the OMS's per-position caps within the first 12 simulated days, then can't open new positions for the remaining 5.5 months because every new attempt is rejected. Every "6-month fulltest" we've run is really a 12-day fulltest.
  - It blocks A1 mark-to-market Sharpe: marking thousands of phantom positions to market gives nonsense equity ($94K → $824K curve), forcing the cost-basis equity curve as the only trustworthy signal.
- **Fix direction**: PaperBroker tracks `cash_available` (initialized from `oms.initial_capital`). On a buy: reject if `cash_available < price * qty + commission`. On a sell: increase cash by proceeds. Live brokers (IBKR) already enforce this via the broker; paper mode needs it too.
